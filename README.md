I chose a multinomial classifier because brewing has three meaningfully different outcomes — success, fizzle, or explosion — rather than a simple pass/fail, so the model needed to output probabilities across all three classes instead of a binary decision. The pipeline takes a player's selected ingredients and stir count for a given spell and runs them through a custom transformer, RecipeMatchTransformer, which converts that raw input into numeric features: how many correct ingredients were included, how many were missing or extra, and how far the stir count deviated from what the spell requires. Those features feed into the classifier, which was trained on synthetic brewing attempts generated to reflect realistic near-misses, not just perfect or completely wrong tries, so the fizzle boundary actually resembles the "close but not quite" range a real player would land in. The bundle also stores the spell data itself and metadata including the exact scikit-learn version used to train it so the Modal deployment installs the identical version the pipeline was fit with, avoiding any mismatch when the model is unpickled. This setup means the API's judgment of a brew genuinely depends on the fitted model rather than a hardcoded rule, since retraining on different synthetic data would shift where the success/fizzle/explode boundaries fall.
